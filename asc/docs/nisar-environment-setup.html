2Key decisions

conda-forge binaries, not a source build

The upstream develop branch is 0.26.0-dev and unreleased, while conda-forge ships 0.25.12 with an identical Python API and the same nisar.workflows entry points. The build machine has no compiler at all — gcc, g++, make, cmake and ninja are all absent — and a pybind11/Eigen compile at meaningful parallelism is a coin-flip against the OOM killer on 13 GB of RAM. Building from source buys nothing here.

Two environments, not one

Two independent constraints force the split:

  • compass 0.5.6 requires scipy <1.13; dolphin 0.42.5 wants scipy ≥1.12. Co-installing pins everything to exactly scipy 1.12.0 and numpy <2.
  • isce2 2.6.x pins libgdal-core ≥3.10.3,<3.11, which drags isce3 back to 0.24.4 (April 2025). Excluding isce2 is what buys 0.25.12.

The isce+ course environment (isceplus2026.yml, env name earthscope_insar) bundles isce2, isce3, compass, dolphin and mintpy together. It does solve — but it resolves isce3 to that 15-month-old 0.24.4. It was not used.

No GPU

The machine has an AMD integrated GPU; nvidia-smi and nvcc are absent. There is no __cuda virtual package, and every *_cuda isce3 build requires __cuda ≥12, so conda selects the _cpu variant automatically. No flag is needed. Verify with hasattr(isce3.ext.isce3, "cuda"), which must be False.

Never set gpu_enabled: true in a NISAR runconfig on this machine. isce3.core.gpu_check.use_gpu() raises on a CPU build. The shipped defaults in share/nisar/defaults/insar.yaml and gslc.yaml are already false, but a JPL production runconfig copied verbatim will not be.

3Installation

Nothing else is required — no mamba install (conda 26.5.3 already defaults to the libmamba solver) and no channel edits (both YAMLs carry nodefaults).

cd /home/sharath/Desktop/work/isce3

conda env create -f asc/env/dolphin_env.yml   # dolphin 0.42.5 + mintpy

4Verification

Beyond verify.sh, this sweep imports every module of every installed package — the only reliable way to catch a missing transitive dependency.

conda run -n isce3_env python -c "
import importlib, pkgutil, warnings; warnings.filterwarnings('ignore')
import nisar, isce3, compass, s1reader
bad = []
for pkg in (nisar, isce3, compass, s1reader):
    for m in pkgutil.walk_packages(pkg.__path__, pkg.__name__+'.', onerror=bad.append):
        try: importlib.import_module(m.name)
        except Exception as e: bad.append(f'{m.name}: {type(e).__name__}')
print('FAILURES:', len(bad)); [print(' ', b) for b in sorted(set(bad))]
"

Expected result: exactly one failure, isce3.cuda — correct on a CPU build. Current state is 331 modules swept, 330 importing cleanly. Anything else in that list is a real gap.

5Credentials

One NASA Earthdata Login covers nearly everything. Register at urs.earthdata.nasa.gov and accept the ASF DAAC license agreements for Sentinel-1 and ALOS.

echo "machine urs.earthdata.nasa.gov login USERNAME password PASSWORD" > $HOME/.netrc
chmod 600 $HOME/.netrc

The chmod is not optional — several tools refuse to run against a world-readable .netrc.

That single file serves: burst download (burst2stack), precise orbits (eof --force-asf), IONEX/TEC from CDDIS, the NISAR DEM, NASADEM, asf_search, NISAR product downloads, and NISAR S3 direct access. No CDSE / Copernicus Dataspace account is required — bursts and orbits come from ASF and the DEM from a public bucket.

Optional: ~/.cdsapirc for PyAPS/ERA5 tropospheric correction (use the CDS Personal Access Token; the legacy key returns 401), and ~/.topoapi for OpenTopography, which the ISCE3/COMPASS path does not use.

6DEM and water mask

The DEM is fetched by sardem --data-source NISAR, which streams from a global VRT at ASF via /vsicurl/ so only the requested bounding box is pulled:

https://nisar.asf.earthdatacloud.nasa.gov/NISAR/DEM/v1.2/EPSG4326/EPSG4326.vrt

This is the Modified Copernicus DEM for NISAR — Copernicus GLO-30 (COP-DEM_GLO-30-DGED/2023_1) with two changes made for NISAR processing: the vertical datum converted from the EGM2008 geoid to the WGS84 ellipsoid, and ocean tiles filled with the EGM2008 geoid model for complete global coverage. Resolution is 1 arcsec (~30 m), EPSG:4326, Float32.

Why the datum matters. ISCE3 geometry (geo2rdr, geocode_slc) requires heights above the ellipsoid. Raw Copernicus GLO-30 ships geoid heights. Over northern Venezuela the undulation runs −9 m to −38 m, so skipping the conversion puts tens of metres of error straight into the range computation.

How to check it in one line: read the ocean. An ellipsoidal DEM reads negative there (≈ −28 m, the negative undulation); a geoid-referenced one reads ≈ 0. Exact zeros across the ocean mean zero-fill, i.e. a broken download.

An independent Copernicus route is available at asc/nisar_workflows/tools/fetch_cop_dem.py, which pulls GLO-30 through Microsoft Planetary Computer's STAC API and converts EGM2008 → WGS84 with gdalwarp. It runs under isce2_env, because planetary-computer and pystac-client are installed there rather than in isce3_env. Cross-checking the two routes over the Caribbean gave −30.54 m and −28.24 m median — agreement to ~2 m from two different pipelines.

The water mask is derived by converting the ellipsoidal DEM back to orthometric (EPSG:4979 → EPSG:9518, EGM2008) via pyproj and thresholding at 0 m — preserving the course's water = (h ≤ 0) semantics.

7Problems encountered

Recorded because most of these fail quietly — the install succeeds, the run completes, and the output is wrong or absent rather than the process erroring.

Environment

P1 python 3.11 silently breaks nisar.workflows.insar
Symptom
Environment installs perfectly. At runtime, from nisar.workflows import insar raises ModuleNotFoundError: No module named 'pyaps3'.
Cause
troposphere.py imports pyaps3 at module scope; pyaps3 hard-depends on pygrib; and conda-forge has no py311 build of pygrib — only py312, py313 and py314.
Resolution
python 3.12 for both environments, with pyaps3 listed explicitly.
P2 Importing isce3 breaks any CLI that takes flags
Symptom
AttributeError on a partially initialised journal module — but only when the tool is invoked with arguments, never in direct testing.
Cause
Importing isce3 pulls in pyre, whose __init__ calls executive.activate() and parses sys.argv at import time. Our --config reached pyre's parser.
Resolution
util.clean_argv() / preload_isce3() — scrub argv before the import, restore it after.
P3 h5py / HDF5 version skew warning
Symptom
UserWarning: h5py is running against HDF5 2.2.0 when it was built against 2.1.0 on every import.
Cause
Every conda-forge h5py 3.16.0 build declares hdf5 ≥2.1.0,<3.0a0 but was compiled against 2.1.0, while libgdal-hdf5 pulls 2.2.0.
Resolution
Benign — do not chase it. HDF5 keeps ABI compatibility within a major version. verify.sh round-trips a gzipped complex64 dataset to prove it. Pinning hdf5=2.1 conflicts with libgdal-hdf5 3.12.4.

Auxiliary data

P4 NASADEM water mask route returns an all-water mask and exits 0
Symptom
A mask covering 100% of the scene, with a successful exit status.
Cause
The SRTMSWBD source 404s. sardem pre-fills its mosaic with 255 = WATER, skips past every tile that fails, and returns success — a silent wrong answer, the worst failure mode of the whole setup.
Resolution
Derive the mask from orthometric heights instead (see §6), and refuse to emit a mask whose water fraction falls outside a sane band.
P5 A missing PROJ grid turns the datum conversion into a no-op
Symptom
None visible. The conversion appears to run and the output looks like a DEM.
Cause
Without us_nga_egm08_25.tif, PROJ falls back to a ballpark vertical transform that applies no geoid at all, returning geoid heights labelled as ellipsoidal.
Resolution
Probe the transform against a published value before using it — EGM2008 undulation at (0°, 0°) is ≈ 17.2 m; measured 17.2251 m. Abort if it returns ≈ 0.

Stale-identity bugs

Four separate failures with one shape: an output identity that omitted something which changes the output, so a stale artifact passed an exists() check. Worth recording as a pattern rather than four coincidences.

P6 Overlay HTML not namespaced by frequency
Symptom
A frequency-A run reported the overlay stage as complete without producing anything.
Cause
Rasters are named ifg_A_HH.* vs ifg_B_HH.* and never collide, but the HTML was a fixed trackG_overlay.html, so the freq-A run found the freq-B page and skipped.
Resolution
Namespace as trackG_overlay_<freq>_<pol>.html.
P7 Interferogram idempotency ignored the geogrid
Symptom
After changing the AOI, the interferogram stage skipped — leaving products describing a different patch of ground.
Cause
Idempotency keyed on filename only; the filename does not encode the geogrid.
Resolution
Compare each existing raster's origin and pixel size against the pin recorded in stack.json and rebuild on mismatch.
P8 Config literals that go stale: reference raster and ocean probe
Symptom
A file-not-found for ifg_B_HH.amp.tif during a frequency-A run; separately, an ocean-probe box falling outside the grid — raising after four minutes of DEM and geoid work.
Cause
Both were literals in the config, set for an earlier frequency and an earlier AOI.
Resolution
Derive the reference raster from the frequency and polarization actually being processed; clamp the probe to the grid, validate it up front, and downgrade a total miss to a warning.

Scientific correctness

P9 Coherence is degenerate at 1×1 looks
Symptom
coherence: median 1.0, >0.3 1.0, valid 1.0 — every pixel perfectly coherent, including open ocean.
Cause
The boxcar estimator averages over the look box. At 1×1 the box is a single sample, and |a·conj(b)| / √(|a|²·|b|²) collapses to exactly 1.0 for every pixel.
Resolution
Estimate coherence over a sliding window centred on each pixel — the same estimator ISCE2 uses for phsig — whenever the look box has fewer samples than the window. Phase stays per-pixel and the output grid is unchanged. Validated against synthetic pairs of known coherence: true 0.60 → 0.615, true 0.00 → 0.170 at a 5×5 window, matching the √π/(2√N) bias of 0.177.

Memory

The workflow stages were first written against a multilooked 6.6 Mpx grid. At full 5 m resolution the same code sees 677 Mpx — 100× more — and every full-grid array becomes a multi-gigabyte allocation.

P10 Full-grid arrays accumulating in the water-mask and unwrap stages
Symptom
OOM kill with no traceback.
Cause
Water mask held five full-grid arrays at once (≈11.5 GB at 677 Mpx); unwrap held the raw interferogram, the filtered copy, a needless .copy() of it, phase-sigma coherence and two boolean masks (≈20 GB).
Resolution
Release arrays as soon as they are dead, build derived products in place, and drop an .astype() that was copying an already-correctly-typed raster.
P11 SNAPHU tiling defeated by its own post-processing
Symptom
OOM immediately at the snaphu call, with no tile output — despite tiling being configured specifically to bound memory.
Cause
Both single_tile_reoptimize and regrow_conncomps default to True, and both run a final pass over the whole grid as a single tile. Tiling kept peak memory at ~3 GB right up until the last step, which then asked for ~65 GB.
Resolution
Both set false when tiling, wired through the config (regrow_conncomps was previously not exposed and silently defaulting to True), and the stage now warns if either is enabled alongside tiling.
P12 Disabling those options fragments the unwrapped phase
Symptom
32 connected components of near-identical size (~1.05 Mpx each), largest covering 3.6% of labelled pixels. The untiled run gave 1 component at 98.6%.
Cause
Component sizes match the tile size, so each component is essentially one tile — the global relabelling step that would merge them is exactly what regrow_conncomps does.
Status
Open Each component carries its own arbitrary 2π offset, so only pixels sharing a label are comparable. The fix is snaphu.io.Raster file-backed I/O, which lets the global pass stream from disk instead of RAM.

9Open issues

  • Connected-component fragmentation at scale (P12) — needs snaphu.io.Raster file-backed I/O so the global relabelling pass can stream from disk. Until then, tiled unwraps above roughly 100 Mpx produce per-tile components.
  • Ionospheric correction is not applied. tec_file is left null, so correct_tec is False. NISAR requires an IMAGEN TEC JSON, not the IONEX format the course downloads, and no downloader ships with nisar. This matters more at L-band than at C-band: range delay scales as K/f², so the same TEC produces roughly 19× the shift at 1.239 GHz versus 5.405 GHz.
  • No azimuth solid-earth tides. geocode_corrections.py computes both components and discards the azimuth one.
  • No troposphere in the GSLC path at all — the term does not appear in gslc.py, geocode_corrections.py or either YAML.
